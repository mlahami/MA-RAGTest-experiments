# ERC6909.sol — User Stories & Specifications

> **Contract:** ERC6909.sol  
> **Solidity Version:** ^0.8.20  
> **Standard:** EIP-6909 (Multi-Token)  
> **Base:** OpenZeppelin v5.5.0  

---

## Overview

A reference implementation of the EIP-6909 minimal multi-token standard. It is a gas-efficient alternative to ERC-1155 for managing multiple fungible token IDs within a single contract. It supports per-token-ID allowances and full operator approvals, and provides internal `_mint`, `_burn`, and `_transfer` hooks for contract extenders.

---

## Actors

| Actor | Description |
|---|---|
| **Token Owner** | Holds balances of one or more token IDs |
| **Spender** | Approved to spend a specific token ID up to a set allowance |
| **Operator** | Approved to manage all token IDs of an owner |
| **Contract Extender** | Developer inheriting this base to add minting/burning logic |

---

## Events

| Event | Emitted When |
|---|---|
| `Transfer(caller, from, to, id, amount)` | Tokens are transferred, minted (`from = 0x0`), or burned (`to = 0x0`) |
| `Approval(owner, spender, id, amount)` | A per-token allowance is set |
| `OperatorSet(owner, spender, approved)` | An operator is granted or revoked |

---

## Custom Errors

| Error | Description |
|---|---|
| `ERC6909InsufficientBalance(sender, balance, needed, id)` | Transfer amount exceeds balance |
| `ERC6909InsufficientAllowance(spender, allowance, needed, id)` | Transfer amount exceeds allowance |
| `ERC6909InvalidApprover(approver)` | Approver is the zero address |
| `ERC6909InvalidReceiver(receiver)` | Receiver is the zero address |
| `ERC6909InvalidSender(sender)` | Sender is the zero address |
| `ERC6909InvalidSpender(spender)` | Spender is the zero address |

## User Stories

### US-01 — Transfer a Token to Another Address

**As a** Token Owner,  
**I want to** transfer a specific amount of a specific token ID to another address,  
**So that** I can send multi-tokens directly without going through an approval step.

**Acceptance Criteria:**
- Caller must have a balance ≥ `amount` for the given token `id`.
- Neither sender (`from`) nor receiver (`to`) may be the zero address.
- Sender's balance decreases and receiver's balance increases atomically.
- A `Transfer` event is emitted with the caller, sender, receiver, token ID, and amount.

**Revert Conditions:**
- `ERC6909InvalidSender` — sender is `address(0)`.
- `ERC6909InvalidReceiver` — receiver is `address(0)`.
- `ERC6909InsufficientBalance` — caller does not have enough of token `id`.

---

### US-02 — Transfer on Behalf of an Owner (transferFrom)

**As a** Spender or Operator,  
**I want to** transfer tokens from an owner's balance on their behalf,  
**So that** protocols and smart contracts can move tokens with the owner's authorization.

**Acceptance Criteria:**
- If the caller is not the owner and is not a global operator, a per-token allowance for `(owner, caller, id)` must cover the `amount`.
- Allowance is decremented by `amount` unless it equals `type(uint256).max` (infinite).
- Operator status (`isOperator(owner, caller) == true`) fully bypasses allowance checks.
- Balances are updated atomically; `Transfer` event is emitted.

**Revert Conditions:**
- `ERC6909InsufficientAllowance` — caller has insufficient allowance and is not an operator.
- `ERC6909InsufficientBalance` — owner does not have enough balance.
- `ERC6909InvalidSender` / `ERC6909InvalidReceiver` — zero address involved.

---

### US-03 — Approve a Spender for a Specific Token ID

**As a** Token Owner,  
**I want to** approve a specific address to spend up to a set amount of a single token ID,  
**So that** I can give granular, per-token spending permissions to contracts or users.

**Acceptance Criteria:**
- `approve(spender, id, amount)` sets `_allowances[owner][spender][id] = amount`.
- Neither owner nor spender may be the zero address.
- An `Approval` event is emitted with the owner, spender, token ID, and amount.
- Setting to `type(uint256).max` grants infinite allowance.

**Revert Conditions:**
- `ERC6909InvalidApprover` — owner is `address(0)`.
- `ERC6909InvalidSpender` — spender is `address(0)`.

---

### US-04 — Grant or Revoke Operator Status

**As a** Token Owner,  
**I want to** grant or revoke full operator access to another address over all my token IDs,  
**So that** I can delegate complete management of my entire multi-token portfolio to a trusted contract or wallet.

**Acceptance Criteria:**
- `setOperator(spender, true)` grants the spender operator rights.
- `setOperator(spender, false)` revokes operator rights.
- Operators bypass all per-token allowance checks in `transferFrom`.
- An `OperatorSet` event is emitted with the owner, spender, and approval status.

**Revert Conditions:**
- `ERC6909InvalidApprover` — owner is `address(0)`.
- `ERC6909InvalidSpender` — spender is `address(0)`.

---

### US-05 — Query Balance and Allowance

**As a** User or Protocol,  
**I want to** read token balances and allowances on-chain,  
**So that** I can make informed decisions before executing transfers or approvals.

**Acceptance Criteria:**
- `balanceOf(owner, id)` returns the owner's balance for a specific token ID.
- `allowance(owner, spender, id)` returns the current spending allowance.
- `isOperator(owner, spender)` returns whether the spender is a full operator for the owner.
- All three are `view` functions with no gas cost when called off-chain.

---

### US-06 — Mint Tokens (Internal — For Contract Extenders)

**As a** Contract Developer extending ERC6909,  
**I want to** use `_mint(to, id, amount)` in my subcontract,  
**So that** I can issue new tokens of a specific ID to an address.

**Acceptance Criteria:**
- `to` must not be the zero address.
- `_balances[to][id]` increases by `amount`.
- A `Transfer` event is emitted from `address(0)` to `to`.
- This function is `internal` and not directly callable from outside.

**Revert Conditions:**
- `ERC6909InvalidReceiver` — `to` is `address(0)`.

---

### US-07 — Burn Tokens (Internal — For Contract Extenders)

**As a** Contract Developer extending ERC6909,  
**I want to** use `_burn(from, id, amount)` in my subcontract,  
**So that** I can permanently destroy tokens of a specific ID.

**Acceptance Criteria:**
- `from` must not be the zero address.
- `_balances[from][id]` decreases by `amount`.
- A `Transfer` event is emitted from `from` to `address(0)`.
- This function is `internal` and not directly callable from outside.

**Revert Conditions:**
- `ERC6909InvalidSender` — `from` is `address(0)`.
- `ERC6909InsufficientBalance` — balance is less than `amount`.

## State Variables

| Variable | Type | Description |
|---|---|---|
| `_balances` | `mapping(address => mapping(uint256 => uint256))` | Token balances per owner per ID |
| `_operatorApprovals` | `mapping(address => mapping(address => bool))` | Operator approvals per owner |
| `_allowances` | `mapping(address => mapping(address => mapping(uint256 => uint256)))` | Per-token allowances |
